# Внутренняя сводка: паттерны desktop mod managers

> **Назначение:** инженерный ориентир для архитектуры **Pantheon** (Tauri + SolidJS + Rust). Это **не** пользовательская документация продукта. Сравнения с внешними проектами и ссылки ниже — только как библиография для разработчиков.

## Зачем этот документ

Фиксирует, как типичные функции мод-менеджера (плагины, профили, install/deploy/conflict) соотносятся с нашим [`mvp.md`](../mvp.md) и как переносить устойчивые идеи в проект на `Tauri + SolidJS + Rust`.

Цель: не копировать чужой продукт 1:1, а повторить проверенную базовую логику в совместимом архитектурном виде.

## 1) Архитектурная модель (что важно для нас)

Типичный desktop mod manager опирается на:

- расширения (плагины);
- централизованное состояние UI + персистентность;
- профили на игру;
- цикл install / deploy / conflict.

### Как это переносим в Pantheon

- Вместо Electron-процессов: `Tauri` + Rust core.
- Вместо обязательного Redux: реактивный UI в `SolidJS` + доменное состояние в SQLite.
- Вместо монолитного extension context: свой **Plugin API v1** с версионированным контрактом.

---

## 2) Плагины и поддержка игр

### Типичные возможности экосистемы

- регистрация игры, установщиков, типов модов;
- реакции на события deploy/install/profile.

### Pantheon MVP

Контракт плагина v1:

- `detectGame`
- `parseMod`
- `planInstall`
- `planDeploy`
- `validate`

Акцент на изоляции и детерминированных планах действий.

---

## 3) Event-driven lifecycle

Упрощённая шина событий v1 в Pantheon:

- `profile:will-change`, `profile:did-change`
- `install:will-start`, `install:did-finish`
- `deploy:will-start`, `deploy:did-finish`
- `conflicts:recalculated`

---

## 4) Installers и маршрутизация модов

- Плагин игры определяет тип мода и возвращает `InstallPlan` / `DeployPlan`.
- В MVP — 1–2 типа модов для пилотной игры.

**Реализация в ядре (аналог Vortex `registerInstaller` + basic installer):** после распаковки архива в staging выполняется **цепочка инсталлеров** по убыванию приоритета (`src-tauri/src/core/installers/`): первый, у кого `test_supported` по списку относительных путей, выполняет `install` и меняет дерево в staging; последний fallback — `BasicInstaller` (без изменений). Состав цепочки задаётся в манифесте плагина (`installers`: id `data-hoist`, `basic`; пустой массив = дефолт). Дополнительно применяются действия из `plan_install` плагина (пути только внутри staging). Финальный список файлов (`walk_staging_with_hashes`) попадает в БД и в `plan_deploy_from_staging`. Поддерживаемые архивы: `.zip`, `.7z`, `.rar` (`core/archive_ext.rs`, `extract_archive_to_staging`; 7z — `sevenz-rust`, rar — `unrar`).

---

## 5) Deploy и конфликты

- Манифест целевых файлов, winner/loser по пути, приоритет.
- Конфликты в UI: победитель, проигравшие, ручной приоритет мода в рамках профиля.

---

## 6) Профили

- Отдельный deploy manifest на профиль.
- Переключение профиля с согласованным состоянием включённых модов (`profile_mods`).

---

## 7) Load order

- Полноценный экосистемный LOOT-аналог не входит в MVP.
- Ручной приоритет (порядок) в профиле — см. ядро и UI.

---

## 8) Merge и post-deploy

- Post-deploy hooks могут расширяться позже; merge по умолчанию выключен.

---

## 9) Discovery

- MVP: ручной путь и стабильный локальный install/deploy.
- Внешние маркетплейсы не блокируют первый релиз.

---

## 10) Приоритеты переноса в Pantheon

1. Расширяемость через плагины (game adapters).
2. Event-driven install/deploy lifecycle.
3. Профили как изолированный контекст.
4. Детерминированный deploy и учёт конфликтов.
5. Понятная модель приоритета модов.

---

## 11) Сознательно не дублируем в первой итерации

- Полный набор событий крупного коммерческого клиента.
- Облачные коллекции и внешние API мод-баз на старте.
- Десятки стратегий установки без необходимости.

---

## 12) Практическая карта соответствия

- `Plugin contract v1` ↔ регистрация игры / установщиков / типов (концептуально).
- `profile switch pipeline` ↔ события смены профиля.
- `deploy hooks` ↔ will/did deploy.
- `conflict recalculation` ↔ пересчёт после изменений модов.

---

## 13) Рекомендации

- Держать файловую логику и транзакции в Rust core.
- В UI не дублировать бизнес-логику конфликтов/deploy.
- Логировать время и результат вызовов плагина.

---

## 14) Вывод

Устойчивый мод-менеджер опирается на event-driven цикл, строгие контракты плагинов и детерминированный deploy с конфликтами. Pantheon закладывает эти основы в своём стеке.
