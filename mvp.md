# MVP: Mod Manager на Tauri + SolidJS с плагинами

## 1) Цель MVP

Собрать рабочий первый релиз мод-менеджера, который:

- поддерживает 1 игру (пилот);
- устанавливает/удаляет моды из архивов;
- использует профили модов;
- расширяется внешними плагинами;
- остается быстрым и доступным (a11y) даже на слабых ПК.

MVP не пытается сразу повторить весь Vortex. Цель — заложить правильное ядро и API, чтобы потом масштабироваться на новые игры и более сложные сценарии.

---

## 2) Границы MVP (что входит и не входит)

### Входит

- Импорт мода из архива (`zip`, базово `7z` при наличии поддержки в выбранной библиотеке).
- Каталог модов: список, статус, версия, источник.
- Включение/выключение мода.
- Удаление с корректной очисткой.
- Профили (минимум: создание, переключение, копирование).
- Базовый конфликт-менеджмент файлов (кто перезаписал кого).
- Плагинная модель для логики конкретной игры.
- Логи операций и понятные ошибки.

### Не входит (перенос в post-MVP)

- Поддержка десятков игр сразу.
- Сложные правила load order уровня LOOT/экосистемных тулов.
- Облачная синхронизация.
- Интеграция с внешними площадками модов через API.
- Встроенный маркетплейс плагинов с рейтингами и отзывами.

---

## 3) Архитектура MVP

## 3.1 Desktop слой

- `Tauri` как контейнер приложения.
- `SolidJS` для UI.
- Связь UI и ядра через Tauri commands (`invoke`).

## 3.2 Core слой (Rust)

- Операции с ФС (копирование/замена/удаление).
- Распаковка архивов.
- Транзакции установки с rollback.
- Подсчет конфликтов и построение deploy-плана.
- Логирование и диагностика ошибок.

## 3.3 Хранилище состояния

- SQLite:
  - игры;
  - профили;
  - моды;
  - файлы модов;
  - транзакции;
  - состояние deploy.

## 3.4 Плагинный слой

- Плагин описывает правила конкретной игры:
  - как обнаружить игру;
  - как интерпретировать архив мода;
  - куда и как деплоить файлы;
  - базовая валидация совместимости.

---

## 4) Контракт плагина (v1)

Минимальный `manifest`:

- `id`
- `name`
- `version`
- `apiVersion`
- `gameId`
- `permissions`

Минимальные хуки:

- `detectGame(context)`
- `parseMod(context)`
- `planInstall(context)`
- `planDeploy(context)`
- `validate(context)`

Принципы:

- Версионируемый API (`apiVersion`), чтобы не ломать старые плагины.
- Ограниченный доступ: только к разрешенным операциям ядра.
- Четкие таймауты/ошибки для хуков.

---

## 5) Основные пользовательские потоки

## 5.1 Первичная настройка

1. Пользователь выбирает игру.
2. Приложение проверяет путь установки.
3. Создается базовый профиль.

## 5.2 Установка мода

1. Выбор архива.
2. Проверка архива и подготовка staging.
3. `parseMod` через game-plugin.
4. Построение install/deploy плана.
5. Выполнение транзакции.
6. Пересчет конфликтов.
7. Обновление UI и логов.

## 5.3 Откат/удаление

1. Выбор мода.
2. Удаление его файлов из активного deploy-состояния.
3. Пересборка состояния победителей конфликтов.
4. Синхронизация профиля и БД.

---

## 6) Модель конфликтов (MVP)

- Единица конфликта: `целевой путь файла`.
- Базовое правило: более высокий приоритет профиля побеждает.
- В UI видно:
  - кто победитель;
  - кто переопределен;
  - откуда пришел файл.
- Ручной приоритет мода (up/down) в рамках профиля.

---

## 7) Безопасность и надежность

- Любая установка = транзакция с журналом шагов.
- При падении/ошибке — попытка rollback.
- Валидация путей (защита от path traversal).
- Нормализация и проверка путей для Windows.
- Лог ошибок, пригодный для диагностики пользователем.

---

## 8) Требования к UI (SolidJS)

Экран MVP:

- Game Overview (игра, путь, статус).
- Profiles.
- Mods List.
- Conflicts.
- Operation Log.

Требования к UX:

- Быстрый поиск по модам.
- Статус операций в реальном времени.
- Ясные тексты ошибок + действие "что делать дальше".

---

## 9) Производительность (frontend best practices)

- Держать в реактивном состоянии только то, что реально нужно экрану.
- Списки модов рендерить с виртуализацией на больших наборах.
- Тяжелые вычисления (индексация, хэши, план deploy) выполнять в Rust, не в UI.
- Делить UI на ленивые чанки (маршруты/крупные панели).
- Минимизировать повторные пересчеты derived-state в Solid.
- Логи и большие таблицы грузить порционно.

Целевые метрики MVP:

- открытие приложения: до 2-3 секунд на типичном ПК;
- переключение профиля: до 500 мс при средней библиотеке модов;
- установка "среднего" мода: детерминированно, с прогрессом и без фризов UI.

---

## 10) Accessibility (a11y) требования

- Полная навигация с клавиатуры (Tab/Shift+Tab/Enter/Escape).
- Видимый `focus` на интерактивных элементах.
- Корректные `aria-label`/`aria-describedby` для кнопок и статусов.
- Контраст текста и состояний не ниже базовых WCAG требований.
- Ошибки и прогресс объявляются для screen reader (live regions).
- Не полагаться только на цвет для конфликтов/статусов.

Definition of done по a11y для MVP:

- Главные сценарии (установка/удаление/переключение профиля) проходят без мыши.
- Нет критичных ошибок в автоматическом a11y-аудите ключевых экранов.

## 12) План реализации (6-8 недель)

### Фаза 1: Foundation

- Каркас Tauri + SolidJS.
- SQLite схема + миграции.
- Базовые сущности: Game/Profile/Mod.

### Фаза 2: Install pipeline

- Импорт архивов.
- Install/remove транзакции.
- Логи операций.

### Фаза 3: Deploy + conflicts

- Построение deploy-плана.
- Первая версия conflict resolution.
- UI экрана конфликтов.

### Фаза 4: Plugins

- API плагина v1 + manifest.
- Пилотный game-plugin.
- Валидация совместимости по `apiVersion`.

### Фаза 5: Quality gates

- E2E сценарии основных потоков.
- Performance профилирование.
- A11y аудит и исправления.

---

## 13) Критерии готовности MVP

MVP считается готовым, если:

- можно поставить, отключить, удалить моды для 1 игры;
- профили работают стабильно;
- конфликты отображаются и управляются базово;
- плагин игры подключается без изменения core-кода;
- есть rollback на ошибках установки;
- ключевые экраны проходят базовые проверки performance и accessibility.

---

## 14) Риски и как снизить

- Разные форматы модов и "сломанные" архивы  
  -> строгая валидация + quarantined staging.

- Ошибки путей/прав в Windows  
  -> централизованный path layer в Rust и понятные recovery-ошибки.

- Разрастание plugin API без контроля  
  -> версия контракта + ADR на изменения API.

- Просадки UI на больших коллекциях  
  -> виртуализация, инкрементальная загрузка, вынос тяжелого в Rust.

---

## 15) Что делать после MVP

- Добавить вторую и третью игру через те же plugin contracts.
- Улучшить conflict engine (зависимости/несовместимости).
- Добавить безопасный auto-update для плагинов.
- Подключить расширенную телеметрию и crash reporting (opt-in).
